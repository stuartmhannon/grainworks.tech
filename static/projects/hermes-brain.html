MAIN LOOP — runs once per API call until the model says done
A. Build API Messages
Sanitize tool calls · Repair alternation · Inject memory + plugin context
  • Sanitize tool_call arguments (repair JSON corruption)
  • Repair message role alternation (tool → user breaks strict APIs)
  • Inject memory context and plugin context into the user message
  • Copy reasoning fields for multi-turn provider compatibility
  • Strip fields strict APIs reject (finish_reason, internal markers)
  • Apply Anthropic prompt caching if using Claude
  • Normalize whitespace and JSON key order for KV cache reuse
  • Strip orphaned tool results, add stubs for missing ones
  • Drop thinking-only assistant turns (Anthropic rejects them)
B. Pre-Flight Checks
Budget consumed? → exit. Interrupt? → exit. Context full? → compress.
  • Iteration budget check: how many API calls used this turn? Exhausted? Hard stop.
  • Budget grace call: one extra chance before the axe
  • Interrupt check: user hit escape? Exit with partial results
  • Context pressure check: estimate request tokens against threshold
  • Deferred to real usage? Skip estimate if recent provider data is better
  • Compression cooldown active? Skip to avoid infinite compress loops
  • Ollama context size check: if GGUF window is physically too small, hard error
C. Call the LLM
Send messages + tools to DeepSeek (or Claude · Ollama · Bedrock · etc.)
  • Streaming: text deltas fire stream_callback as they arrive
  • TTS pipeline can start generating audio before full response
  • Non-streaming: wait for complete response
  • Retry loop (up to max_retries): jittered exponential backoff (5s base, 120s cap)
  • Rate limited (429)? Backoff and retry
  • Server error (500/502)? Backoff and retry
  • Overloaded (503/529)? Backoff and retry
  • Timeout (504/524)? Backoff and retry
  • Content filter hit? Hard stop, explain refusal to user
  • Max retries exhausted? Try fallback provider, if none → hard error

D. Execute Tools
Guardrail check before every tool · sequential or parallel (up to 8 workers)
  • Guardrail checks each tool by name and arguments before execution
  • Destructive commands (rm, sudo, docker rm -f): warn user or block
  • Idempotency check: same tool + same args + same result? Skip.
  • Budget check: track token usage per tool call
  • Sequential path: one tool at a time (most tools)
  • Concurrent path: up to 8 parallel workers (independent reads)
  • Guardrail fires after each result: failure detection + classification
  • Guardrail halt? Synthesize "tool denied" result, agent explains why
  • Post-tool: compress context if near limit
  • Append tool results to messages → loop back to top
E. Finalize Response
The model produced text with no tool calls — this is the answer.
  • Normal case: content delivered to user
  • Empty after tool calls: nudge model once to continue processing
  • Thinking-only: model produced reasoning fields but no text → let it self-continue
  • Truncated mid-tool-call: retry with doubled output budget (4 attempts max)
  • Partial stream delivery: use whatever text arrived before connection died
  • Content filter hit: inform user the model declined to respond
  • Failed fallback: return error message with diagnostic details
  • Persist messages to session DB
  • Clean up task resources (VM, temporary files)
  • Return final response to caller
